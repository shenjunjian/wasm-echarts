底层原理

给能读 JS、想搞懂 WASM 的前端：option 怎么进引擎、为什么只有一份 WASM、 函数和像素怎么过桥。三层定位见 站点首页。

从 facade 到 RGBA

业务 / site → js/index.js → 主线程 handle 或 Worker → pkg → ZRenderer → RGBA

wasm-echarts 与 wasm-zrender 是 sibling，共用同一份 ZRenderer。 echarts 页不得再加载 wasm-zrender/pkg。

option 管线

OptionValue → merge → GlobalModel → ChartView → Storage

函数字段保留为 OptionValue::Function，渲染 / 交互阶段再回调。 notMerge / replaceMerge 来自 setOption 第二参数，不是 option 根字段。

步骤 源码 做什么
解析 option/ JS object → Null / Bool / Number / String / Array / Object / Function
preprocessor / processor js/extension.js 入 WASM 前改 option
模型 model/、scheduler.rs grid / 轴 / series / dataZoom 窗口
落笔 render.rs、各 chart/ 往同一份 ZRenderer 加图元

单 WASM

getZr 与 ChartView 共用 ZR_REGISTRY。 echarts 的 js/native.js 加载 pkg/wasm_echarts.js 后立刻 setNative 进 zrender 的 native-core，图元 native 类来自这一份模块。

因此 echarts 页不得再加载 wasm-zrender/pkg：那会变成第二份内存、第二份 fontdb。 zrender 文档站可以继续单独用自己的 pkg。

JS ↔ WASM：三种过桥

1. 普通数据

option 解成 Rust OptionValue，再进 GlobalModel。 LinearGradient 等 wasm-bindgen 实例按 getter 收成 type / colorStops。 

chart.setOption({
  series: [{
    type: 'line',
    areaStyle: { color: new graphic.LinearGradient(0, 0, 0, 1, stops) },
    data: [1, 2, 3],
  }],
});

2. 函数

主线程把 js_sys::Function 留在 option 树里。渲染 / tooltip / custom 时 call1：tooltip.formatter、axisLabel.formatter、 itemStyle.color、symbolSize、series.renderItem。

WASM 必须与定义这些函数的 JS 在同一 realm。因此 Worker 路径禁止函数 option （结构化克隆会失败）。对照 interactive。

3. RGBA 回图

refresh() → Vec<u8> → JS Uint8Array。 绑了 canvas 时 facade 做成 ImageData 再 putImageData。 mousemove 仅在 hover / axisPointer / 拖拽导致画面变化时上屏。

Worker 数据流

用法见 运行模式。这里只写实现向的过桥。

facade → postMessage(option) → Worker 内实例 → SAB / Transferable → 主线程 blit

option 方向一律结构化克隆，不用 SharedArrayBuffer。 SAB 只用于回传 RGBA。指针只传 x, y，tooltip 文案回主线程 DOM。

文件 职责
js/worker-protocol.js 消息名；option 含函数检测；SAB 探测
js/worker-bridge.js 主线程桥：创建 module Worker、RPC、字体与地图同步
js/chart.worker.js Worker 内 initWasm + EChartsInstance

字体 / 地图由 facade 代发，开发者不必第二份消息。 getZr() 的 ZRender 在 Worker 里，主线程拿不到。
